Current Role

Seal records evidence before authority exists.

Seal currently serves as a local integrity and evidence surface, report-only verification lane, policy regression target, manifest/hash baseline mechanism, and bridge toward future runtime-boundary work.

Boundary Model

Seal is organized around explicit evidence layers.

Each layer is a record boundary. Current work is planning, metadata, reports, and guarded validation rather than enforcement.

Contract layer

Vocabulary, evidence boundaries, non-claims, and promotion rules.

Report layer

Deterministic no-effect status records about what Seal supports.

Evidence layer

Records for contracts, reports, artifacts, state transitions, and authority decisions.

Capability layer

Narrow, inspectable, future signed capability-envelope direction.

Signature layer

Future signing direction for manifests, reports, releases, gates, and authority decisions.

Integrity bridge

Future Linux/Fedora integrity evidence, package evidence, and host validation bridge.

Canonical Boundary

Seal is not a production security product.

The documentation explicitly forbids claims of production security readiness, runtime enforcement, root authority, network authority, Fedora approval, malware prevention, or broad host protection until reproducible evidence supports them.

Allowed now

Contract definition, implementation planning, report-field design, evidence-record design, status alignment, and guard validation.

Forbidden now

Tool execution, host reads or writes, network operations, key generation, signature verification, runtime authority, and production hardening claims.
